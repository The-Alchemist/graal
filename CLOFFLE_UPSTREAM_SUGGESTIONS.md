## Suggestions, ranked by value for the effort

### 0. Done: `null` guest value treated as "no value" on boxing-eliminated slow paths

Fixed in [oracle/graal#14535](https://github.com/oracle/graal/pull/14535) (branch
`fix-bytecode-null-guest-value`). Nothing left to do here; later references to "item 0"
mean this bug (`store.local$Long` receiving `null` throws `FrameSlotTypeException`).

### 2. Constant pool deduplication must preserve object identity (correctness)

Bytecode constants can be arbitrary objects, but
`BytecodeSupport.ConstantsBuffer.add` deduplicates them by `==` **or `equals`**.
Published bytes: `fastAdd` does `if_acmpeq` and then `Object.equals`, and `mapGet`
does `Object.equals`.
Source on `main`:
`truffle/src/com.oracle.truffle.api.bytecode/src/com/oracle/truffle/api/bytecode/BytecodeSupport.java`
~183-211 and ~337-346.

This is not specific to any guest language.
Java's `equals` contract expresses value equality, not that either reference can
replace the other in all contexts.
Two equal objects can have observably different identity, runtime classes,
metadata, or state.
For example, two instances can compare equal while carrying different payloads;
if they are supplied to separate `emitLoadConstant` calls or constant operands,
the current pool replaces the second instance with the first.
Operations can observe the change through `==`, `getClass()`, or the payload.

Serialization has the same issue independently of `ConstantsBuffer`.
The generated `SerializationState.objects` in
`truffle/src/com.oracle.truffle.dsl.processor/src/com/oracle/truffle/dsl/processor/bytecode/generator/BuilderElement.java`
~9306-9418 is a `HashMap<Object, Integer>`, so equal, distinct constants also
receive one serialized object ID.
A complete fix must cover both normal bytecode construction and serialization.

Recommended fix: deduplicate constants by identity throughout.
Repeated use of the same reference should share a pool slot or serialized object
ID, while distinct references should remain distinct regardless of `equals` and
`hashCode`.
That means using `==` and `System.identityHashCode` in `ConstantsBuffer`, and an
`IdentityHashMap` for serialized objects.
This is a semantic correction and does not require a language-specific hook.
If changing the default is considered too disruptive for constant-pool footprint,
a global `@GenerateBytecode` policy that controls both paths is a compatible
fallback.
Adding only `ConstantsBuffer.addIdentity(Object)` would be insufficient: generated
builders cannot select it, and serialization would still merge equal objects.

Tests should cover equal-but-distinct objects below and above
`ConstantsBuffer.HASH_THRESHOLD`, `LoadConstant` and constant operands in a
generated interpreter, and a serialization round trip.
They should also verify that repeated use of the same reference is still shared.

Cloffle is one concrete downstream example: structural equality can currently
collapse values with different metadata or concrete types.
The fix would remove
`src/jvm/net/javacrumbs/cloffle/bytecode/IdentityConstant.java` and the metadata
workaround in `ExprToBytecodeLiterals.java` (~463-470).

### 3. `ConstantsBuffer.add(null)` throws (tiny)

`add` starts with `Objects.requireNonNull`, which is present in the published bytes,
while `addNull()` exists and serialization already has `CODE_$CREATE_NULL`
(`BuilderElement.java` ~9407). Cloffle works around it with `TYPE_FALSE_SENTINEL`
in `CloffleBytecodeSerializer.java`.

Proposed fix: have `add(null)` delegate to a single shared null slot, or document
the sentinel pattern for null-valued constant operands. Check first whether
`addNull()` is safe to call repeatedly. Its javadoc says the reserved null slots
are meant to be patched later, so a shared-null path may be what's needed.

### 4. Clearing locals under boxing elimination (docs; possibly nothing to fix)

With the default `illegalLocalException` (`FrameSlotTypeException`), the built-in
`ClearLocal` and the block-exit clears call `frame.clear(index)`, which marks the
slot `Illegal`. Published generated code: `handleClearLocal` calls `FRAMES.clear(frame, frame_index)`.
The boxing-elimination Object `load.local` path then throws on the `Illegal` slot.

Upstream already supports `defaultLocalValue`: `emitClearLocal` becomes
`setFrameObject(..., "DEFAULT_LOCAL_VALUE")`
(`BytecodeInstructionHandler.java` ~1518-1527). With 25.4.4.1.1, Cloffle confirmed the
generated `handleClearLocal` becomes `FRAMES.setObject(frame, idx, DEFAULT_LOCAL_VALUE)`,
and `defaultLocalValue = "null"` fully replaced its custom op with no test regressions
(Step 0 experiment A). **So this is a doc suggestion only:** point to
`defaultLocalValue` from the `boxingEliminationTypes`, `ClearLocal` and
`enableBlockScoping` javadoc as the way to keep cleared slots Object-typed.

### 5. Attach exception locations automatically (docs, or a small default)

Exceptions thrown from operations have a null location. Cloffle rebuilds it in
`interceptTruffleException` using a dummy `SourceSectionLocationNode`
(`BytecodeExceptionBoundary.java` 37-68, `ClojureException.java` 433-444). The hooks
receive `bytecodeIndex`, so `bytecodeNode.getSourceLocation(bytecodeIndex)` is
available.

Proposed fix: add a documented recipe to the `BytecodeRootNode.interceptTruffleException`
javadoc, or optionally have the generated code fill in the location when it is missing.

### Not an upstream issue: `createLocal(name, info)`

A Cloffle doc claims naming a local "shifts the locals table". That's false in
25.4.4.1.1. The generated `Builder.createLocal()` is `createLocal(null, null)`, and
`frameIndex = USER_LOCALS_START_INDEX + scope.getFrameOffset() + scope.getNumLocals()`
doesn't depend on the name. The real obstacle is that Cloffle pre-allocates a pool
of root locals before binding names are known. At most, suggest a javadoc line
saying names are metadata only. A `setLocalName` after creation would help only
if Cloffle keeps the pool.

## Considered and rejected as "small"

- Catching host exceptions in guest `try`/`catch`. It's a deliberate design choice (`interceptInternalException`), and the feature would be medium-sized.
- A setter on `ContextThreadLocal`. Also deliberate; a mutable holder is the intended pattern.
- Removing the need for `sun.misc.Unsafe`, and the dropped darwin-amd64 `libtruffleattach`. Both are known and large, or decided upstream.
- Varargs overhead in `Value.execute`, and inlining-budget bailouts. Cloffle solves these on its side, and there's no small upstream fix.

## Cloffle Step 0 (checked before filing items 4 and 5)

Worktree: `/Users/karl-medplum/.cursor/worktrees/cloffle-clojure/step0`, branch
`step0-bytecode-options`, based on Cloffle `60635525`.

Each run used `clojure -T:build run-tests` (JUnit, 1300 tests) and
`clojure -T:build run-clj-tests` (660 tests, 19,130 assertions), both starting from a clean `target`.

| Run | Change | JUnit | Clojure suite |
|-----|--------|-------|---------------|
| Baseline (`60635525`) | none | 1242 pass, 1 fail | 0 failures |
| A (`86bcdb08`) | `defaultLocalValue = "null"`; built-in `ClearLocal` replaces custom `ClearLocalToNull` | 1242 pass, 1 fail (same) | 0 failures |
| B (`51671bde`) | A + `enableBlockScoping = false` + no seeded root-local pool | 1233 pass, 10 fail | aborts during bootstrap |

The single failure in the baseline and A is environmental:
`ComparePerformanceTest.testEndToEndSmokeRun` couldn't get the JMH lock because
another JMH instance is running on the machine.

Every B failure is item 0's `FrameSlotTypeException`. With the pool gone, Object
locals start untagged, quicken to `$Long`, and then receive `nil`. Commit `8c3af427`
(on top of A) adds `StoreLocalNullAfterPrimitiveTest`, which passes on A and fails on B.

Conclusions:
- Item 4 is solved on the Cloffle side by `defaultLocalValue`. Upstream only needs docs.
- Root scoping (`enableBlockScoping = false`) is viable for Cloffle only if Object
  locals keep being seeded, or once item 0 is fixed upstream. The seeded pool is
  effectively a workaround for item 0.
- Named locals: `createLocal(name, info)` is safe (see above). Adopting it in Cloffle
  needs locals to be created where the binding name is known, i.e. after the pool is
  removed. So it waits on item 0 too.
- Performance was not benchmarked for A. Only correctness suites were run.

Local build gotchas found while doing the earlier fixes:
- Set `JAVA_HOME=/opt/homebrew/opt/graalvm/libexec/graalvm.jdk/Contents/Home`. The
  Homebrew root has no `release` file, and `mx` rejects it.

  the generated `*Gen.java` under `mxbuild/jdk25/<project>/src_gen/` to confirm.
